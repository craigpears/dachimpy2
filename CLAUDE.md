`npm i --no-save --no-package-lock node@22 wrangler@4`; node_modules is ignored). Wrangler 3 on Windows serves no
files from subfolders, so don't use it.

Modular, no technical debt (the user, 10 Nov: "we need to make sure I'm not creating spaghetti or just mess"):
- Each puzzle (Carpentry, Gunnery, Bilge, Swordfight, Treasure Haul, rowing...) is one module with one
  implementation of its rules, knowing nothing of where it's played, used everywhere it's played. Gunnery on the
  gun tower and on the sloop, Carpentry on the wall, her deck and the crane, are the same puzzle code with thin
  wrappers for what's drawn round them, never a copy per place. When a puzzle still in a js/den file is needed
  somewhere new, move its rules into a TypeScript module in `src/` (like `bilge.ts`) first, then share it.
- The same goes for the world's objects and scenes (a lock, a gun, a crane, a ship, a place on the sea): each a
  module of its own that can be reused, not code smeared across files. Introduce this gradually as the world grows:
  when a change would copy code or tangle two parts together, pull the shared part out first.
- Places and events as little islands (the user, 11 Nov, after the Wedding Isle: "I like that we can add like
  these little islands of different events, and it's not like compounding in complexity. Each is relatively
  isolated, can work"): a new place or event is its own island in the code too (its rules in `src/`, its 3D in
  its own `js/den/` files, its lines in `src/lines/`), touching the rest only through a few thin hooks (a
  square on the sea, a quest line, a cheat, what comes home with you). Keep that seam thin as more are added.

- Server and client kept apart, a modular monolith (the user, 12 Nov: "server code is separated from client
  code in a way that it can easily be shifted later"). Rules in `src/` are shared and pure: no DOM, no
  sockets, randomness and the clock passed in (`random = Math.random` only as a default), so the same code
  can run in the browser, in a Cloudflare room, or on a proper server later. Anything a server does (a
  room's logic) is a pure class in `src/` taking messages and the time and returning messages; `worker/`
  holds only thin adapters around it (sockets, hibernation); the browser reaches it through a small link
  (WebSocket, or in-process in the same tab for single-player and tests), never a socket directly.
